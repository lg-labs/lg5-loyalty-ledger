## Architecture overview

The service mirrors the canonical 8-module shape from `blank-service`
(RULE-004) under the Maven `groupId: com.lg.platform.loyalty`,
`artifactId` prefix `lg5-loyalty-ledger-`:

```
lg5-loyalty-ledger-domain/
  ├── lg5-loyalty-ledger-domain-core         # Aggregates (Movement, CustomerBalance, ProcessedInputEvent), domain event (CustomerBalanceUpdatedEvent), value objects. NO Spring (RULE-003).
  └── lg5-loyalty-ledger-application-service # Inbound listeners' helper, outbox helper, outbox scheduler, mappers (domain ↔ payload, payload ↔ Avro), input ports.
lg5-loyalty-ledger-api                       # REST controllers (GET /loyalty/customers/{id}/{balance|movements}); media type vnd.api.v1+json (RULE-006).
lg5-loyalty-ledger-data-access               # JPA entities (movement, customer_balance, processed_input_event, outbox), repositories, Postgres ENUM mappings, Flyway migrations.
lg5-loyalty-ledger-message/
  ├── lg5-loyalty-ledger-message-core        # Kafka producer/consumer beans, listener classes (one per inbound topic), Avro <-> domain mappers.
  └── lg5-loyalty-ledger-message-model       # Outbound Avro schemas (BalanceUpdateCause.avsc, CustomerBalanceUpdatedAvroModel.avsc). Inbound schemas are *consumed* via order-service-message-model Maven dep (ADR-002).
lg5-loyalty-ledger-container                 # @SpringBootApplication entrypoint; application.yaml (test+local profiles); IT setup (Lg5TestBoot[PortNone]).
lg5-loyalty-ledger-acceptance-test           # Cucumber + Testcontainers + Wiremock; one feature file per REQ (cf. RULE-012/013).
lg5-loyalty-ledger-support                   # docker-compose for local infra (Postgres + Kafka + Schema Registry).
```

Build: Maven multi-module; parent POM is
`com.lg5.spring:lg5-spring-parent:1.0.0-alpha.<short-git-sha>`
(RULE-002 — pinned to lg5-spring SHA `cbb6783`, matching the bundle's
`bundle.lg5-spring-sha`).

## Cross-cutting concerns

- **Topics / channels.** Three inbound topics (`order-paid`,
  `order-cancelled`, `order-refunded`) are **provisioned by the
  `order-service` team**; we configure consumer subscriptions only.
  The one outbound topic (`customer-balance-updated`) is **provisioned
  by us** in the platform's standard topic-management process; partition
  count to be sized in M3 (proposal: 6 partitions, replication 3 — to
  be confirmed with the platform-ops team). Owner: `lglabs` (this
  feature) for outbound; `order-service` team for inbound.
- **Schema registry.** Compatibility mode `BACKWARD` (RULE-007) for
  both `BalanceUpdateCause` and `CustomerBalanceUpdatedAvroModel`.
  Registration is automated via the Confluent schema-registry plugin
  invoked from `make run-avro-model` then `make publish-schemas`. Owner:
  `lglabs`.
- **Observability.** Structured logging (JSON) emits one log line per
  inbound event with `event_type`, `event_id`, `order_id`, `outcome`
  (cf. ADR-003 `outcome` enum). One dashboard panel per REQ-005 and
  REQ-002/Q1 case (`NOOP_DEBIT_WITHOUT_CREDIT` rate;
  `NOOP_ZERO_CREDIT` rate); SLA alert on `p95(write_path_lag) > 5s`
  (PRD §4 / Q6). Owner: `lglabs` (placeholder; in a real platform this
  would be the SRE team).
- **Security.** Read endpoints are **internal-only** (Q5) — no
  end-user authentication beyond the platform's standard mTLS / mesh
  policy; no per-customer authorization (the caller is a trusted
  service that already resolved the customer identity). No secrets
  beyond Kafka & Postgres credentials, managed via the standard config
  prefixes (RULE-014: `kafka-config.*`, `loyalty-ledger-service.*`,
  `spring.datasource.*`). Owner: `lglabs` (placeholder).
- **Data lifecycle.** No retention policy in v1 (PRD §6: ledger is
  append-only and grows). `processed_input_event` also grows linearly
  with inbound traffic; archival is documented as known-future-work in
  ADR-003. Owner: `lglabs`.

## Risks

| ID | Risk                                                                                                                                          | Likelihood × Impact | Mitigation                                                                                                                               | Owner   |
|----|-----------------------------------------------------------------------------------------------------------------------------------------------|---------------------|------------------------------------------------------------------------------------------------------------------------------------------|---------|
| R1 | Upstream `order-service` evolves `OrderPaidAvroModel` (e.g. renames `paidAmount`) without bumping in a `BACKWARD`-compatible way.             | low × high          | Pin a known-good version of `order-service-message-model` in our `pom.xml`; consume new versions deliberately; ATDD covers field decode. | tech lead |
| R2 | `processed_input_event` storage growth becomes the dominant cost.                                                                             | medium × medium     | Document archival as known-future-work in ADR-003; revisit in v2 with a partitioned table or a periodic compaction job.                  | SRE     |
| R3 | The outbox scheduler lag exceeds the SLA target (`p95 < 5s`).                                                                                 | low × medium        | Tune scheduler `fixedDelayString`; benchmark with a realistic Kafka producer in M3 IT. Fall back to a smaller delay if needed.           | tech lead |
| R4 | A consumer of `customer-balance-updated` is built before the `UNKNOWN` enum default reaches it, causing a hard error on a future cause symbol. | low × medium        | Day-one `default: "UNKNOWN"` on the enum (already in ADR-005); release notes call this out.                                              | tech lead |
| R5 | The `paid → cancelled → paid-again` legitimate-replay case (Q9) is mis-implemented as a no-op due to the long-standing instinct to key idempotency on `(orderId, eventType)`. | medium × high | Dedicated ATDD scenario for the sequence; ADR-003 + this risk row prominently linked from `tasks.md`; code review by `lg5-code-reviewer` subagent. | tech lead |
| R6 | A negative-balance customer causes an unintended downstream side-effect (e.g. promotions engine assumed `balance >= 0`).                      | low × low           | Out of scope for this service (Q3 explicitly defers alerting to subscribers). Communicate to subscriber teams in release notes.          | PO       |
