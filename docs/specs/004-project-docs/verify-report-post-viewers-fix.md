### 9. BUG-4 — Swagger UI / AsyncAPI viewers never served (P1, REQ-003 + REQ-004)

| Field | Value |
|---|---|
| Severity | P1 |
| REQ impact | REQ-003 (sync contract reachable), REQ-004 (async contract reachable) |
| How caught | Stakeholder visited `/api/` and `/events/` on the live Firebase surface after v0.2.0 was committed; observed only the page `<h1>` (Markdown content) with no embedded Swagger UI or AsyncAPI viewer. Both prior reports had probed only the section *landing* pages (which returned 200 because VitePress generated `index.html` from the Markdown), and never probed the viewer assets themselves. |
| Root cause | VitePress static-asset wiring. CI was copying viewer HTMLs (`swagger-ui.html`, `asyncapi.html`) and raw spec YAMLs to `docs/site/{api,events}/*.html` — but VitePress treats those directories as Markdown source roots and **drops any non-Markdown file** during build. Static assets must live under `docs/site/public/` (VitePress's documented public dir), which is copied verbatim into `dist/`. |
| Remediation | PR #9 (squash `627dd0a`), fix commit `300d7b1`: <br>• `c-integration.yml` (both `docs-build-pages` and `docs-build-firebase`): redirect viewer-HTML + raw-YAML copy targets from `docs/site/{api,events}/` to `docs/site/public/{api,events}/`. <br>• `docs/site/scripts/check-artifacts.mjs`: updated expected paths to `public/api/swagger-ui.html` and `public/events/asyncapi.html`. <br>• `docs/site/api/index.md` + `docs/site/events/index.md`: added visible CTAs "Open the Swagger UI →" / "Open the AsyncAPI viewer →" with **relative-path** links (`./swagger-ui.html`, `./asyncapi.html`) so VitePress base-rewriting handles both DOCS_BASE values (`/lg5-loyalty-ledger/` on Pages, `/` on Firebase). |
| Live verification | Against `627dd0a`: 8 URLs probed (4 viewer/spec assets × 2 surfaces); all 200 with correct titles + content sizes. See §4. |
| Lesson learned | **Any non-Markdown content that must be served by a VitePress site (raw HTML, JS, YAML, JSON, images, etc.) must live under `docs/site/public/`.** VitePress silently drops non-Markdown siblings of Markdown source files. Pre-merge CI did not catch this because: (a) the build succeeded (no error), (b) `check-artifacts.mjs` looked at the wrong path, (c) linkinator only probes intra-Markdown links and never followed a CTA into the viewer HTML (the CTA didn't exist yet). The post-merge visual probe was the only mechanism that could surface it — confirming again the value of TASK-012-style live verification beyond CI gates. |
| Process implication | The matrix for REQ-003/REQ-004 in v0.2.0 should have probed not just the section landing but the viewer asset specifically. v0.3.0 (this report) bakes that into §1 + §4. Future docs features should treat "every linked non-Markdown asset returns 200" as part of the REQ acceptance probe. |
