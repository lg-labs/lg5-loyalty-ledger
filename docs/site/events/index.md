# Events (asynchronous contract)

This page is the entry point to the **Kafka surface** of `loyalty-ledger`. It
is intentionally short: the canonical contract lives in the AsyncAPI document
(mirroring the Avro schemas), and the conceptual model lives on the
architecture page.

## What this surface is for

`loyalty-ledger` is event-driven on the write side. The Kafka surface is how
the rest of the platform talks to the ledger:

- **Inbound** — three order-domain topics that are translated into ledger
  movements (`order-paid` → credit, `order-cancelled` → debit, `order-refunded`
  → debit).
- **Outbound** — one balance-update topic published via the Transactional
  Outbox after a movement has been appended.

Downstream consumers (notifications, analytics, other read models) should not
poll the REST API to detect changes. They should subscribe to the outbound
topic instead.

## How to read the spec

A few interpretation rules that are easy to miss when reading the AsyncAPI
document in isolation:

- **Avro is the source of truth on the wire.** The AsyncAPI schemas are
  JSON-Schema mirrors of the canonical `.avsc` files under
  `lg5-loyalty-ledger-message/lg5-loyalty-ledger-message-model/src/main/resources/avro/`.
  Producers and consumers serialize Avro; AsyncAPI exists to document the
  shape for humans and AsyncAPI tooling.
- **Topics live in configuration, not in the spec title.** Topic names are
  resolved from `loyalty-ledger-service.topics.*` in
  `lg5-loyalty-ledger-container/src/main/resources/config/application.yaml`
  and can be overridden per environment.
- **Inbound idempotency is mandatory.** Every inbound message is deduped on
  `(messageId, eventType)` via the `processed_messages` table before any
  side effect runs. Re-delivery is safe; design downstream test fixtures
  accordingly.
- **Outbound publishing goes through the outbox.** The service does not
  publish to Kafka inside the transaction that appends a movement. A scheduled
  relay reads `OutboxMessage` rows and publishes them with at-least-once
  semantics. Downstream consumers must therefore be idempotent too.
- **Traceability:** every outbound message carries the `messageId` of the
  inbound event that caused it, which is the join key for end-to-end tracing.
