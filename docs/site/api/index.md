# API (synchronous contract)

This page is the entry point to the **read-only HTTP surface** of
`loyalty-ledger`. It is intentionally short: the canonical contract lives in
the OpenAPI document, and the conceptual model lives on the architecture page.

## What this surface is for

`loyalty-ledger` does not accept loyalty operations over HTTP. The ledger is
driven by inbound business events from the order domain. The HTTP API exists
only to expose read models that downstream readers (UIs, support tools,
back-office services) can query without subscribing to Kafka.

In practice the API answers two questions about a single customer:

- *what is the current point balance?*
- *which ledger movements produced that balance?*

That scope is deliberate. It is the same scope documented in detail under
[Architecture → REST](../architecture/rest).

## How to read the spec

A few interpretation rules that are easy to miss when reading the spec in
isolation:

- **Media type:** every response uses the vendor-versioned media type
  `application/vnd.api.v1+json`. The version lives in the media type, not in
  the URL path. Clients should send `Accept: application/vnd.api.v1+json`.
- **Spec-first, enforced in CI:** the OpenAPI document is the source of
  truth, and every REST integration test runs through a Swagger request
  validator filter that fails the build if a response drifts from the spec.
  You can therefore trust the spec to describe the live behavior.
- **Error envelope:** all `4xx` and `5xx` responses share a single problem
  shape (`code`, `message`, `traceId`, optional `details`). The `traceId` on
  `5xx` is server-minted and is the correlation key to use when reporting a
  problem.
- **Pagination:** the movements endpoint returns a page cursor in the
  response body. The cursor is opaque — clients should treat it as a token
  and pass it back unchanged.
- **No write endpoints:** the absence of `POST` / `PUT` / `PATCH` /
  `DELETE` on `/loyalty/**` is intentional, not a documentation gap. Writes
  happen via the event surface; see the linked architecture pages.
